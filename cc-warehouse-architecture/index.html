The deep end (leave it alone)

The foundation already has the shape the cards below aim for. store.py hides O_EXCL takeover races and atomic writes behind put / get / acquire_lock / verify_walk. capture.capture_transcript is one deep ingestion seam with three adapters (hook, sweep, migrate) and no caller re-implements dedupe or error paths. render.py puts 747 lines behind three functions. The oracle suite drives public seams only, proves the F5 zero-object-reads negative with an audit hook, and fault-injects store.atomic_write cleanly. Friction concentrates in the parser→render→build/share stretch and in cli.py, not here.

Fresh proof the deep seam earns its keep (2026-07-19, after this review's scan): relocate exposed that atomic_write silently reset an existing target's permissions on every rewrite, a defect present since slice 01. The fix landed in the ONE primitive and every caller inherited it, pinned by tests/test_store_regressions.py. That is locality doing exactly what this board keeps asking for.

In plain English. The storage engine, the ingestion pipeline, and the test harness are in excellent shape; every suggestion on this board is about the layers above them. A bug just found in the write primitive was fixed once, in one place, and everything downstream got the fix for free - which is the whole argument of this board in miniature.

After: one parse, three consumers

flowchart TB

Problem. parser.py sells two products over the same bytes - parse_session and build_conversation - and each re-runs _extract_entries (parser.py:158, parser.py:403). render.py's emitters take raw bytes, so build.py's one projection extracts the payload five times (render.py:375-377, 726-727, 740; build.py:84-86). DESIGN section 4 says parse ONCE; the interface defeats it.

Solution. One parse entry extracts entries once and yields metadata and conversation together; the emitters accept the parsed model, with the bytes form kept only at the edge.

  • leverage: one parse, three emitters
  • locality: extraction quirks in one function
  • 5x parse cost gone before the 7k-session migrate and v1.1 FTS5
  • makes the DESIGN parse-ONCE sentence true (R8)
In plain English. Every time the tool turns one saved conversation into its four output files, it re-reads and re-decodes the same raw file five times. The fix: decode it once and hand the decoded result to all four outputs. Same results, a fifth of the work, one less way for the readers to disagree.

Evidence: VERIFIED first-hand at snapshot 56262f6. Contract ties: R8, R9; DESIGN section 4.

Problem. The lock primitive is deep (store.py:192-271) but the ceremony around it is shallow and copied: the sentinel triple plus acquire-or-refuse plus finally-release appears in sweep.py:24-29/137-151, build.py:218-227/247-280, migrate.py:34-39/99-119, relocate.py:39-40/634-641. cli.py then re-implements the lock-held detector, failure loop, stored/built count, summary line, and exit policy five times (cli.py:187-195, 242-250, 491-502, 597-617, 684-698). reports.py fails the deletion test today: 19 lines, one property, the real R10 behavior lives in its callers.

Solution. reports.py absorbs the protocol: run a batch body under locks/<op> or return the standard lock-held report, and present any BatchReport to console plus exit code in one place. Verbs keep only their bodies; the lock stays store's O_EXCL primitive (R14 untouched).

  • locality: R10 and R14 presentation in one module
  • deletes four sentinel triples and five CLI blocks
  • shrinks exactly the cli.py surface 12a, 12b, and 13 must touch
In plain English. Five commands all follow the same ritual: take a lock so two copies never run at once, work item by item, then print what failed and set the exit code. That ritual is copy-pasted into each command. Write it once and every current and future command inherits it; a fix to the ritual fixes all five at once.

C3 · Make the risky transforms public and I/O-free

PROPOSED Strong in-process

src/cc_warehouse/share.py · relocate.py

Before: testing one redaction rule

sequenceDiagram
  participant T as test
  participant H as ccw hook subprocess
  participant C as catalog.sqlite raw SQL
  participant S as ccw share subprocess
  participant O as out dir rglob
  T->>H: stage JSONL, run hook
  T->>C: SELECT short WHERE hash
  T->>S: share --out
  T->>O: read every html/md, assert

After: the interface is the test surface

sequenceDiagram
  participant T as test
  participant D as detector / rewriter (pure)
  T->>D: decoded text, mapping
  D-->>T: hits / rewritten text

Problem. The correctness-critical logic of the two riskiest verbs is pure transformation, yet all of it is private and reachable only through Config-plus-disk entry points: share's detectors _scan_secrets / _is_generic_secret / _redact_tree (share.py:117-278, only share() public) and relocate's JSON-aware rewriter _form_patterns / _sub_text / _sub_tree / _rewrite_bytes (relocate.py:114-184, only plan/apply public). Locality is lost: a redaction miss lives in _scan_secrets, but the test that catches it runs three process boundaries away (test_share_regressions.py:30-49: hook subprocess, raw SQL, share subprocess, rglob). Every share/relocate/sweep/migrate test file drives the CLI only; direct imports are zero.

Solution. Expose the transforms as public, I/O-free interfaces: decoded text in, hits out; text or JSON node plus mapping in, rewritten result out. The verbs keep the I/O shell around them. store.atomic_write already proves this shape works in this suite.

Timing update (2026-07-19 split): ticket 12b re-opens exactly the relocate rewriter surface - its carried-forward findings (locale-dependent read_text, JSON reformatting, silent scan drops) are all rewriter-core defects. Folding the I/O-free rewriter seam into 12b's work order costs almost nothing extra and gives that slice the in-memory test surface it currently lacks. The share half of this card stands alone and is not gated on 12b.
  • interface becomes the test surface for the riskiest logic
  • a new redaction rule: one in-memory assertion
  • locality: boundary-case bugs land beside their logic
  • oracle tests stay locked; every future test gets cheaper
In plain English. The two most dangerous features - scrubbing secrets before sharing, and rewriting paths when a project moves - keep their core logic locked away where tests cannot reach it directly. Checking one scrubbing rule today means building a fake warehouse, running two commands as separate programs, and digging through the output files. Expose the core as plain text-in, answer-out functions and a new rule becomes a one-line test.

Evidence: VERIFIED first-hand at snapshot 56262f6 (the call-pattern census is AGENT-REPORTED, spot-verified). Contract ties: ticket 12b for the rewriter half.

Problem. "A head is a row no other row supersedes" is core version-chain semantics with no owner. The predicate SQL is typed verbatim twice (build.py:137 and build.py:167) while the head_for_short docstring claims one owner, R9 - an overclaim the code does not honor (R8/F6). _Head is private, so share re-declares the identical five-field shape as _Resolved and copies it field by field (share.py:73-82, 320-328). cli.py runs its own session and project SELECTs (cli.py:300, 422). Understanding one concept means bouncing catalog to build to share.

Solution. catalog.py owns the head predicate, a public head-record type, and the handful of read queries; build, share, and the CLI consume them. Reads stay catalog-only (R6 unchanged).

  • locality: version-chain semantics live beside the schema
  • leverage: v1.1 search and v1.2 MCP read the same seam
  • deletes the _Resolved shape copy
  • makes the one-owner docstring true (R8)
In plain English. The database question "which copy of this session is the current one?" is answered by query text pasted in two places, and a third file re-creates the same record shape because the original is private. Put the question, its answer, and the record type in one place next to the schema, and everyone asks it the same way.

Problem. Above the shared block fragment, the traversal is written twice: _render_turn (render.py:314) and _turn_html (render.py:675) carry the byte-identical synthetic-skip guard (render.py:315, 678) and the same prompt/reminders/blocks order. A change to turn grouping or the synthetic rule is two edits with no type keeping them in lockstep; this doubling is why render.py is 747 lines.

Solution. Hoist the turn and page traversal into one walker yielding typed rendered units; markdown and HTML become thin serializers of those units. Outputs are frozen by black-box tests, so the refactor verifies itself.

  • locality: turn policy decided once
  • one implementation of the walk (R9)
  • pairs naturally with C1's single parse product
In plain English. The markdown files and the web pages are produced by two separate loops that walk the conversation in exactly the same order with exactly the same rules. Change how turns are grouped and you must remember to change both. Walk the conversation once; let markdown and HTML just format what the walk hands them.

C6 · cli.py: verbs hand back results, not cursors

PROPOSED Worth exploring in-process

src/cc_warehouse/cli.py · build.py · relocate.py

Before: cli.py cross-section (727 lines)

verb dispatch (fine)
hand-rolled flag parsing x5 (ticket 13, scheduled)

After: thin presentation edge

verb dispatch

Problem. The interface of cli.py is a trivial dispatch, but its implementation carries verb logic: it opens the catalog and encodes the no-row-vs-superseded policy for render (cli.py:297-310), runs the project-exists SELECT (cli.py:419-430), and holds the F9 warehouse-safety guard (cli.py:340-356). That guard does not travel: a future non-CLI caller of ad-hoc rendering, such as the v1.2 MCP server, bypasses it entirely. A verb behavior change routinely edits two files.

Solution. Each verb module owns its catalog reads and safety guards and returns a result plus exit intent; cli.py keeps parsing, printing, and exit-code mapping. Scoped deliberately to exclude flag parsing and config layering, which ticket 13 already owns. Timing note (2026-07-19 split): cli.py is also on 12a's and 12b's TOUCHES lists, and 12a's carried-forward plan-advisory consent gap overlaps this card's action-string coupling; whatever 12a/12b decide for relocate's CLI surface should land before this card generalizes it.

  • locality: one file per verb change
  • the F9 guard travels with the operation, not the entry point
  • leverage: the v1.2 MCP surface reuses whole verbs
In plain English. The command-line front door does more than route commands: it runs its own database lookups, holds the safety check that stops a render from overwriting the warehouse, and knows other files' internal status words. Move that knowledge into the feature files so the front door only parses, calls, and prints - and so the safety check still applies when something other than the command line calls the feature.

C7 · Type the Block discriminant

PROPOSED Worth exploring in-process

src/cc_warehouse/parser.py · render.py

Before

kind: str  # 9 values, listed in a docstring

consumers re-switch on string literals:

_render_block · _render_machinery · block.kind == "tool_result" x2

pyright strict cannot flag a missed or renamed kind: content silently drops (the F6 class)

After

kind: Literal[9 kinds]  # stdlib, R7-safe

exhaustive matches are compile-checked; the field-validity rules (tool_name only with tool_use) move from prose into the type

Problem. Block.kind is a bare str spanning nine values whose taxonomy and field-validity rules live only in a docstring (parser.py:258-272). Producers and every consumer must independently know them; render.py re-derives the switch three ways (render.py:242, 262, 643/668). Adding or renaming a kind is a silent-drop hazard the type checker cannot see - exactly FINDINGS F6.

Solution. Make kind a typed discriminant (Literal or a small per-kind type, both stdlib). A missed case becomes a pyright error instead of dropped content.

  • F6 silent loss becomes a compile-time error
  • interface carries the taxonomy; the docstring stops being load-bearing
In plain English. Every piece of a conversation carries a plain text label like "thinking" or "tool_use", and the list of valid labels lives only in a comment. Add or rename a label and nothing warns the code that forgot to handle it - that content just quietly vanishes from the output. Make the label list a real type and the checker flags every forgotten spot before it ships.

Evidence: VERIFIED first-hand at snapshot 56262f6. Contract ties: F6, R7.

Problem. render_html emits conversation content and page chrome as one indivisible page: the highlight.js script tag pointing at cdnjs.cloudflare.com is appended unconditionally (render.py:536-540, 710). share.py's only render path is build.write_projection (share.py:389), so every page on a published shared site makes every viewer's browser call out to a third-party CDN. There is no adapter between rendering the conversation and wrapping it in a page, so shares cannot differ from personal projections.

Solution. A seam between content emission and chrome assembly. Personal projections keep the CDN plus fallback exactly as DESIGN section 6 sanctions; shares gain the ability to inline or omit it - once that decision is made.

Contract callout: DESIGN section 15 item 8 explicitly holds shares-inline-vs-CDN OPEN, and the grill round locked shares to the personal renderer and theme. This card proposes only the seam that makes the open decision implementable; choosing the share behavior is the principal's contract call, not a code change.
  • two adapters justify the seam: personal chrome, share chrome
  • unblocks the section 15 item 8 decision
In plain English. Pages you share currently load their code-highlighting script from a public server, so everyone who views a shared page pings a third party. The renderer cannot do otherwise because the page wrapper and the conversation content are welded together. Separate them and shared pages can carry the script inside the page - once you decide they should; that call is yours, held open in the design doc.

Seen, but already ticketed (not re-proposed)

Two frictions every lens flagged are ticket 13's explicit scope, so they are recorded here rather than carded: (1) the five hand-rolled flag scanners in cli.py, each annotated "full flag layering lands in slice 13"; (2) config.toml parsed in three modules (config._webhooks_from_root, share._custom_patterns, relocate._relocate_roots) while Config's redact_patterns / relocate_roots / voice_* / inbox fields sit unpopulated - the ticket orders load_config completed in place, "a parallel loader is a rejection (R9)". Cards C2 and C6 are sized to complement that slice, not collide with it.

Post-scan additions (the 2026-07-19 slice-12 split, commits fcadd7e / 69f27e6 / 56262f6): C10's connection churn moved into this category when ticket 12b listed it as a carried-forward finding; the 12a/12b split also resolves the wait-for-slice-12 timing caveats this board placed on relocate-touching candidates, and DESIGN section 11 plus SPEC 10.2 now record the boundary-rule CORRECTION and the frozen relocate rulings (cross-device refused, no undo/resume, TOCTOU residual accepted, JSON keys included, backup covers content-rewritten files only).

In plain English. Two known annoyances - hand-rolled flag parsing and the config file being read in three different places - are already on the roadmap as the final slice, so they are listed here only to show they were seen, not missed. Since this board's first pass, the risky "move a project" feature was split into two smaller, safer work orders, and one of this board's minor suggestions (C10) is now on that work order's list, so it stopped being a suggestion and became a plan.

Top recommendation

C1 - Parse once: one parse product

Zero contract risk, no collision with in-flight slice work, and the modules it touches are done and frozen by black-box output tests, so the refactor verifies itself. It removes a 5x cost from the exact path the ~7k-session migration and v1.1 FTS5 indexing will hammer, makes DESIGN section 4's parse-ONCE sentence true, and lays the spine C5 serializes from. Next best: C2, best done before the queue ahead of it lands - 12a, 12b, and slice 13 all touch cli.py, and v1.1's ccw import would copy the batch protocol a fifth time. C3's relocate half has a new natural home: fold the I/O-free rewriter seam into ticket 12b's work order.

In plain English. Start with the decode-once fix: it is safe (the existing tests prove the outputs stay identical), it cannot collide with the work in flight, and it speeds up exactly what the coming 7,000-session import will hammer hardest.
